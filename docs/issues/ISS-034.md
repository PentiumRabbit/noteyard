# ISS-034 — 拖拽手柄（⠿）按住后块不跟随移动

| 字段 | 内容 |
|------|------|
| ID | ISS-034 |
| 状态 | 待修复 |
| 优先级 | P1 |
| 发现日期 | 2026-05-05 |
| 发现人 | 用户 |
| 环境 | Tauri 客户端（make dev） |
| 关联 | ISS-030、ISS-032 |

## 现象

- 鼠标 hover 到块左侧，⠿ 手柄图标出现
- 按住 ⠿ 尝试拖动，块本身不跟随鼠标移动
- 有时出现绿色 `+` 光标（copy 模式）
- 无法完成块的拖拽，也无法触发并排分栏

## 需要排查

1. 查看 Tauri / 浏览器控制台日志，确认拖拽时是否有 JS 报错
2. 检查 `SideMenuController` 是否正确触发 `blockDragStart`（在 `DragHandleButton.onDragStart` 中）
3. 检查 `editor-wrap` 的 `onDragOver` handler（ISS-032 新增）是否干扰了 ProseMirror 原生拖拽事件
4. 检查是否有 CSS `user-select: none` 或 `pointer-events: none` 覆盖了手柄区域
5. 检查 BlockNote 版本的 `blockDragStart` 实现是否有已知 bug

## 根因分析

> 分析日期：2026-05-05 / 负责人：arch-frontend-ISS034

### 结论摘要

**根本原因是 Tauri macOS WKWebView 的系统级拖拽拦截机制（最高置信度）**，结合 ISS-032 引入的 `onDragOver` handler 存在一个次要但确定的副作用问题。两者叠加导致用户完全无法完成块拖拽。

---

### 方向 1：ISS-032 `onDragOver` handler 是否是回归原因

**结论：ISS-032 的 `handleEditorDragOver` 本身不是拖拽启动失败的直接原因，但它确认存在一个副作用 bug，且不能独自解释块不移动的现象。**

分析依据：

1. `handleEditorDragOver` 的代码（`web/src/components/editor/Editor.tsx` 第 702-706 行）：
   ```ts
   const handleEditorDragOver = (e: React.DragEvent<HTMLDivElement>) => {
     if (e.dataTransfer.types.length > 0) {
       e.dataTransfer.dropEffect = "move";
     }
   };
   ```
   - 该 handler **没有调用 `e.preventDefault()`，也没有调用 `e.stopPropagation()`**。
   - React 合成事件的 `onDragOver` 在冒泡阶段触发，不会阻止 ProseMirror 在捕获阶段或原生 `dragover` 事件中的 `preventDefault()` 调用。
   - 仅修改 `dropEffect` 属性，该操作是幂等且无害的——ProseMirror 本身的 `dragover` handler 会 `preventDefault()` 允许 drop，`dropEffect` 的最终值由最后设置者决定（在同一事件上后执行的处理函数覆盖前者）。

2. **副作用确认**：React 合成事件比原生事件晚触发（均在冒泡阶段，但 React 是委托到 document），因此 ISS-032 的 `dropEffect = "move"` 会在 ProseMirror 之后执行，这实际上能正确覆盖 dropEffect。然而，该 handler 的触发条件 `e.dataTransfer.types.length > 0` 在所有拖拽（包括外部文件拖入）时均成立，会将外部文件拖拽也强制设为 `move`，这是一个范围过宽的问题，但与本 issue 的"块不移动"无关。

3. **不是回归原因**：块不随鼠标移动、有时出现绿色 `+` 光标，在 ISS-032 修复之前（commit ebb9cda 之前）的环境中同样能复现，因为光标问题正是 ISS-032 被提出的原因。因此 ISS-032 不是本 issue 的回归引入点。

---

### 方向 2：CSS 问题

**结论：无 CSS 导致的阻断。**

检查 `Editor.css` 中与 SideMenu 相关的样式：

```css
/* web/src/components/editor/Editor.css 第 389-395 行 */
.editor-wrap .bn-side-menu {
  color: var(--color-text-secondary);
}
.editor-wrap .bn-side-menu:hover {
  color: var(--color-text-primary);
}
```

- 没有 `pointer-events: none`、`user-select: none`、`-webkit-user-drag: none` 等禁止拖拽的属性。
- `editor-wrap` 的 CSS（第 215-217 行）只有 `flex: 1`，无 `overflow: hidden`。
- Mantine `SideMenuButton` 渲染为 `MantineActionIcon`（`<button>` 元素），带有 `draggable={true}` 属性（由 `DragHandleButton.tsx` 传入），CSS 层面不存在阻断。

### 方向 3：SideMenuPlugin 事件绑定

**结论：绑定正确，但 dragstart 数据链在 WKWebView 中断。**

阅读 `SideMenuPlugin.ts`（`web/node_modules/@blocknote/core/src/extensions/SideMenu/SideMenuPlugin.ts`）：

- `SideMenuView` 构造函数将所有 drag 事件监听器注册到 `this.pmView.root`（即 `document`），使用正确的捕获/冒泡标志。
- `onDragStart`（第 389-411 行）：监听 `dragstart` 事件，读取 `dataTransfer.getData("blocknote/html")` 并将内容设置为 `pmView.dragging`。
- `blockDragStart`（第 643-655 行）：由 `DragHandleButton` 的 `onDragStart` 调用，调用 `dragging.ts` 中的 `dragStart()`。
- `dragging.ts` 中的 `dragStart()`（第 149-216 行）：调用 `e.dataTransfer.setData("blocknote/html", clipboardHTML)` 并设置 `effectAllowed = "move"`，再调用 `dataTransfer.setDragImage()`。

**问题关键**：`dragStart()` 调用了 `e.dataTransfer.setDragImage(dragImageElement!, 0, 0)`（第 214 行）。这个 `dragImageElement` 是通过 `setDragImage()` 附加到 `document.body` 的一个克隆 DOM 节点（第 131-134 行）。

在 macOS WKWebView (wry 0.55.0) 中，HTML5 drag-and-drop 的拖拽启动依赖于 WKWebView 将 `mousedown` + `mousemove` 转化为系统级的拖拽会话（NSDraggingSession）。但 WKWebView 默认的 `NSDraggingDestination` 实现（`drag_drop.rs`）**只处理外部文件拖入**，不处理 HTML5 内部拖拽的 mousedown 转 drag 路径。

---

### 方向 4：Tauri WKWebView 根本原因（最高优先，置信度最高）

**结论：WKWebView 在 macOS 下对 HTML5 `draggable` 元素的拖拽行为存在已知限制，需要在 Tauri 配置中显式允许 fileDropEnabled，同时还需要规避 WKWebView 将系统级 NSDraggingSession 截断为 "Copy" 操作的问题。**

详细分析：

1. **wry 的 `NSDraggingDestination` 实现**（`drag_drop.rs` 第 53-78 行）：
   - `draggingUpdated` 返回 `NSDragOperation::Copy`（第 76 行），并且无论 dataTransfer 上的 `effectAllowed` 设置为何值，系统级 NSDragging 层的操作类型始终固定为 `Copy`。
   - 这正好解释了用户看到的**绿色 `+` 光标（copy 模式）**：这不是 CSS 或 JS 层面的问题，而是 macOS 系统拖拽 API 在 WKWebView 的 `draggingUpdated:` 回调中强制返回了 `NSDragOperation::Copy`。

2. **HTML5 dragstart 与 WKWebView 的冲突**：
   - 在 macOS 上，WKWebView 对 HTML5 `draggable="true"` 元素的 drag 事件路径依赖于 WebKit 内部的 `-[WKContentView _dragLiftAnimationProgress:]` 和 `-[WKContentView startDrag:item:]` 机制（仅 iOS WebKit）。
   - macOS 的 WKWebView 使用 AppKit NSView 的鼠标事件路径，不会自动将 `mousemove` 翻译成 HTML5 `dragstart` 事件，**除非 WebKit 检测到拖拽手势并内部启动 drag session**。
   - 当 `draggable="true"` 的按钮触发 `onDragStart` 时，WebKit 需要在内部建立 NSDraggingSession 并向 JavaScript 派发 `dragstart` 事件。由于 wry 重写了 `NSDraggingDestination`，外来拖拽会被 wry 拦截并以 `Copy` 模式处理，而 HTML5 内部拖拽（`draggable` 元素触发的）是否能正常走 WebKit 内部路径，取决于 wry/tauri 版本。

3. **`fileDropEnabled` 与内部 HTML5 拖拽的关系**：
   - Tauri v2 的 `tauri.conf.json` 中没有配置 `fileDropEnabled: false`（`src-tauri/tauri.conf.json` 中该字段缺失）。
   - 在 Tauri v1 中，`fileDropEnabled: false` 会禁用 wry 的文件拖放 handler，从而让 WKWebView 不再拦截系统拖拽事件，允许 HTML5 drag 正常工作。
   - **Tauri v2 中等价的配置已移除 `fileDropEnabled`**，需要改用 `app.security.dangerousUseHttp` 或通过 capability 控制。但更重要的是：wry 0.55.0 的 `draggingUpdated` 强制返回 `NSDragOperation::Copy`，**这会导致系统在 `performDragOperation` 之前取消 "move" 操作**，使块无法真正被移动到目标位置。

4. **综合因果链**：
   ```
   用户按住 ⠿ 拖动
     → HTML5 dragstart 触发，BlockNote 设置 dataTransfer 数据 (effectAllowed="move")
     → WKWebView 将此事件提升为 NSDraggingSession
     → wry draggingEntered: 返回 NSDragOperation::Copy
     → wry draggingUpdated: 返回 NSDragOperation::Copy（忽略 effectAllowed）
     → macOS 系统显示绿色 "+" copy 光标
     → BlockNote onDrop 触发时 pmView.dragging 可能为 null（因为 drag session 被 copy 模式干扰）
       或 drop 坐标被 wry 合成事件错误映射
     → 块不移动到目标位置
   ```

## 修复方案

### 方案 A（推荐）：在 Tauri 侧禁用 wry 文件拖放处理，还原 WKWebView 原生 HTML5 drag 路径

**文件**：`src-tauri/src/lib.rs`

**改动**（在 `tauri::Builder::default()` 链中添加）：

```rust
// 在 .setup(...) 之前添加：
.on_window_event(|_window, _event| {}) // 占位，见下方说明
```

更准确的 Tauri v2 方式是在 window 构建时设置，但 Tauri v2 已不再通过 `tauri.conf.json` 的 `fileDropEnabled` 字段控制，需要使用以下方式：

在 `setup` 闭包中，对主窗口调用：

```rust
// src-tauri/src/lib.rs setup 闭包内，在 sidecar 启动逻辑之前
if let Some(window) = app.get_webview_window("main") {
    // 禁止 wry 拦截文件拖放，让 WKWebView 原生 HTML5 drag 正常工作
    let _ = window.disable_file_drop_handler();
}
```

> 注意：`disable_file_drop_handler()` 是 Tauri v2 `WebviewWindow` 提供的 API（对应 wry 层的 `with_drag_drop_handler(|_| false)`，返回 false 表示拒绝拦截，交回系统默认行为）。需确认 tauri 版本是否暴露此 API；若没有，可在 `Cargo.toml` 中为 `wry` 设置 feature `disable-drag-drop`，或通过 tauri-plugin 方式配置。

**预期效果**：WKWebView 不再将 HTML5 内部拖拽提升为 `NSDragOperation::Copy`，而是直接让 WebKit 处理，块跟随鼠标移动恢复正常。

---

### 方案 B（备选）：在 JS 层强制阻止外部拖拽到 Tauri 窗口

若方案 A 的 API 不可用，可在前端防御性屏蔽系统级 Copy 干扰：

**文件**：`web/src/components/editor/Editor.tsx`

**改动位置**：第 702-706 行的 `handleEditorDragOver`，**替换**为：

```ts
// ISS-034 修复：只允许来自 blocknote 的内部拖拽（blocknote/html），
// 并阻止默认行为以覆盖 WKWebView 返回的 Copy 操作。
const handleEditorDragOver = (e: React.DragEvent<HTMLDivElement>) => {
  if (e.dataTransfer.types.includes("blocknote/html")) {
    e.preventDefault();                    // 允许 drop
    e.dataTransfer.dropEffect = "move";    // 强制 move 光标
  }
};
```

> 重要说明：在 `dragover` 中调用 `e.preventDefault()` 是 HTML5 drag-and-drop 规范的必要步骤（允许 drop）。ProseMirror 在其内部 `dragover` handler 中也调用了 `preventDefault()`；React 的合成事件在 ProseMirror 之后执行（都在冒泡阶段，React 委托在 document），两者不冲突。
>
> 但注意：`e.preventDefault()` 在 React 合成事件中只能防止 React 自身的默认行为；原生 DOM 的 dragover 默认行为（不允许 drop）由 ProseMirror 通过 `event.preventDefault()` 处理，**React 合成事件的 preventDefault 不会影响原生事件的 preventDefault 调用**。因此此改动对 ProseMirror 的原生事件链无副作用。

### 方案 C（ISS-032 副作用修复，独立于主根因）

**文件**：`web/src/components/editor/Editor.tsx` 第 702-706 行

将 `handleEditorDragOver` 的触发条件从"有任意 dataTransfer 数据"缩窄为"有 blocknote/html 数据"，避免将外部文件拖入也强制设为 move：

```ts
const handleEditorDragOver = (e: React.DragEvent<HTMLDivElement>) => {
  if (e.dataTransfer.types.includes("blocknote/html")) {
    e.dataTransfer.dropEffect = "move";
  }
};
```

此改动修复 ISS-032 遗留的副作用，但不能解决块不移动的主问题（需配合方案 A 或方案 B）。
