# ISS-039 — 斜杠菜单下方空间不足时未翻转到上方

## 现象

在编辑器靠近底部的块中输入 `/` 触发斜杠菜单，菜单始终向下弹出被截断，未自动翻转到光标上方显示。

## 已尝试方案

通过 `SuggestionMenuController` 的 `floatingOptions` prop 覆盖 middleware，传入 `flip({ padding: 240 })`，无效。

## 根因分析

`SuggestionMenuController` 内部调用 floating-ui 的 `useFloating`，middleware 顺序为：
```
offset(10) → flip() → shift() → size()
```

问题：`size()` 会把 `maxHeight` 压缩到 `availableHeight`，但 `flip()` 在 `size()` 之前执行，此时 floating 元素还没有被撑开到真实高度（菜单内容是动态渲染的）。floating-ui 的 `flip` 基于 floating 元素当前的 `height` 判断是否放得下——如果菜单还未渲染完成或高度为 0，flip 看不到真实高度，不会翻转。

另外 `flip({ padding: 240 })` 的 `padding` 含义是 reference 四周的碰撞检测内边距，不是 floating 元素需要的最小剩余空间，所以设大 padding 也无效。

## 正确修复方案

使用 floating-ui 的 `autoPlacement` 替代 `flip`，或在 `size()` middleware 的 `apply` 函数中检测可用高度，若 < 阈值则手动切换 placement。

更简单可靠的方案：在 `size()` middleware 中，当 `availableHeight < 200` 且上方空间更大时，通过修改 floating 元素的 `transform` 实现视觉翻转——**但这不是 floating-ui 的标准用法**。

**推荐方案（floating-ui 标准）**：

在 `floatingOptions` 中，用 `size` middleware 的 `apply` 同时处理翻转逻辑：

```ts
middleware: [
  offset(10),
  flip(),        // flip 必须在 size 之前
  shift(),
  size({
    apply({ availableHeight, availableWidth, elements }) {
      Object.assign(elements.floating.style, {
        maxHeight: `${Math.max(availableHeight - 10, 100)}px`,
        maxWidth: `${availableWidth}px`,
      });
    },
  }),
]
```

关键：floating-ui 的 `flip()` 工作原理是在 middleware 计算阶段检测 **reference 上下方的可用空间**，与 floating 元素实际高度无关——它比较 `referenceRect.bottom` 到 viewport 底部的距离 vs `referenceRect.top` 到 viewport 顶部的距离，选择空间更大的一侧。

因此 **默认的 `flip()` 本应生效**。需要排查的是 `SuggestionMenuController` 的 reference 是否正确设置为光标位置的 DOMRect，以及 viewport 边界检测是否在 Tauri WKWebView 中正常工作（Tauri 的 `visualViewport` 可能与桌面浏览器不同）。

## 待排查

1. Tauri WKWebView 的 `window.innerHeight` / `document.documentElement.clientHeight` 是否等于可见区域高度
2. `SuggestionMenuController` 传入的 referencePos（光标 DOMRect）的 `bottom` 值是否正确
3. floating-ui 使用哪个 boundary 做碰撞检测（默认是 `clippingAncestors`，若编辑器容器有 `overflow: hidden` 可能导致 boundary 不是 viewport）

## arch-frontend-ISS039 根因确认（2026-05-05）

### 根因一：SuggestionMenuController 未使用 FloatingPortal，菜单 div 挂载在 overflow-y:auto 容器内

经代码审查确认（`@blocknote/react/dist/blocknote-react.js` 第 2785 行）：

```js
// Tr() 的返回值 — 直接返回 div，无 FloatingPortal 包裹
return !h || !g || ... ? null :
  /* @__PURE__ */ i("div", { ref: p, style: M, ...B(), children: ... });
```

`FloatingPortal`（变量名 `Wt`）在整个文件中**只在第 3422 行出现一次**，仅用于 Table 句柄 widget，**斜杠菜单没有使用**。

这意味着斜杠菜单 `div` 渲染在 `BlockNoteView` 的 DOM 树内，其祖先链为：

```
.editor-wrap > .bn-container > ... > [floating div]
.main (overflow-y: auto)
.app  (overflow: hidden)
```

### 根因二：floating-ui clippingAncestors 以 .main 作为 boundary，flip 的边界不是 viewport

floating-ui 的 `boundary = 'clippingAncestors'`（默认值）在 `getClippingElementAncestors()` 中遍历 floating 元素的 DOM 祖先，收集所有 `overflow` 非 `visible` 的元素（见 `@floating-ui/dom/dist/floating-ui.dom.esm.js` 第 312-341 行）。

项目中的 overflow 祖先：
- `.main` → `overflow-y: auto`（`App.css` 第 9 行）
- `.app` → `overflow: hidden`（`App.css` 第 4 行）

`getClippingRect` 对所有 clipping ancestors 取**矩形交集**（第 354-365 行）。由于 `.main` 是可滚动容器，其 `getBoundingClientRect()` 返回的是**可见视口区域**（通常等于 viewport 高度），但这个矩形的 `bottom` 值会随滚动位置而变化。

**实际问题**：当用户在编辑器底部块输入 `/` 时，光标（referencePos）的 `bottom` 值接近 `.main` 可见区域底部。flip 比较"光标到 boundary.bottom 的距离"与"光标到 boundary.top 的距离"，**此时 boundary 是 `.main` 的可见矩形**。由于 `.main` 的可见区域本身就占满整个 viewport，这个计算在 `.main` 不滚动时等同于 viewport。

**但关键在于**：`.app` 有 `overflow: hidden`，这个元素也成为 clipping ancestor，其 `getBoundingClientRect().height` 是 `100vh`。floating-ui 取所有 clipping ancestors 的**最小交集**，最终 boundary 高度仍然是 viewport 高度，逻辑上 flip 应当生效。

### 根因三（实际根因）：`floatingOptions` 的 middleware 完全替换默认值，但 flip boundary 受 .main overflow-y:auto 影响

查看 `Tr()` 函数（第 2756-2784 行）：

```js
const { isMounted: h, ref: p, style: M, getFloatingProps: B } = G(
  ...,
  {
    placement: "bottom-start",
    middleware: [ A(10), W({ mainAxis: true, crossAxis: false }), le(), Se({...}) ],
    ...d   // floatingOptions 展开在最后，完整覆盖 middleware
  }
);
```

`...d`（floatingOptions）展开在对象末尾，因此自定义 `middleware` 数组**确实完整替换**了默认数组。`flip({ padding: 240 })` 已经生效传入，问题不在传参。

**真正的根因**：

1. 菜单 div 位于 `overflow-y: auto` 的 `.main` 容器内（非 FloatingPortal）
2. `isTopLayer()` 检测（用于跳过 clipping ancestors）依赖 `:popover-open` 或 `:modal` CSS 伪类，普通 `div` 不满足，因此 `getClippingElementAncestors` 正常收集 `.main` 和 `.app`
3. `.main` 的 `overflow-y: auto` 使其成为 clipping ancestor，但其可见矩形 bottom 在用户滚动到底部时**已经是 viewport 底部**——此时 flip 判断上方空间更大，**理论上应翻转**
4. **实际不翻转的原因**：`size()` middleware 在 flip 之后执行，在 `apply` 中将 `maxHeight` 设为 `availableHeight - 10`。当 flip 判断下方空间不足而翻转为 `top-start` 时，`availableHeight` 变为上方空间高度；但若菜单 DOM 初始高度为 0（首次渲染），flip 在第一次 middleware 计算时使用的是**旧高度 0**，认为下方"空间足够"（0px 高度的元素放得下），不触发翻转。这是 floating-ui 的已知问题：**虚拟 reference + 动态内容高度导致首帧 flip 判断错误**。

### 修复方案（eng 实现指引）

**方案 A（推荐）：显式指定 `boundary: document.documentElement`**

在 floating-ui 中，将 boundary 设为 `document.documentElement` 可以跳过 `.main` 的 clipping 影响，直接用 HTML 根元素（等同于 viewport）作为判断边界：

```ts
// web/src/components/editor/Editor.tsx
import { offset, flip, shift, size } from "@floating-ui/react";

const suggestionMenuFloatingOptions = {
  placement: "bottom-start" as const,
  middleware: [
    offset(10),
    flip({
      boundary: document.documentElement,  // 强制用 viewport 而非 .main
      fallbackAxisSideDirection: "start",
      padding: 10,
    }),
    shift({ boundary: document.documentElement }),
    size({
      boundary: document.documentElement,
      apply({ availableHeight, elements }: { availableHeight: number; elements: { floating: HTMLElement } }) {
        Object.assign(elements.floating.style, {
          maxHeight: `${Math.max(availableHeight - 10, 80)}px`,
        });
      },
    }),
  ],
};
```

**方案 B：使用 `autoPlacement()` 替代 `flip()`**

`autoPlacement` 在每帧重新计算最优位置，不受首帧高度为 0 的影响：

```ts
import { offset, autoPlacement, shift, size } from "@floating-ui/react";

const suggestionMenuFloatingOptions = {
  middleware: [
    offset(10),
    autoPlacement({
      boundary: document.documentElement,
      allowedPlacements: ["bottom-start", "top-start"],
    }),
    shift({ boundary: document.documentElement }),
    size({
      boundary: document.documentElement,
      apply({ availableHeight, elements }: { availableHeight: number; elements: { floating: HTMLElement } }) {
        Object.assign(elements.floating.style, {
          maxHeight: `${Math.max(availableHeight - 10, 80)}px`,
        });
      },
    }),
  ],
};
```

注意：`autoPlacement` 与 `placement` 选项不兼容，需去掉 `placement: "bottom-start"`。

**方案 C（最彻底）：为菜单 div 包裹 FloatingPortal**

若上述方案效果不稳定，在 `Editor.tsx` 中自定义 `SuggestionMenu` 渲染，外层包裹 `FloatingPortal`，将菜单挂载到 body，彻底脱离 `.main` 的 overflow 上下文。但这需要 fork `SuggestionMenuController` 实现，成本较高。

**推荐优先执行方案 A**，改动最小，直接在已有 `suggestionMenuFloatingOptions` 中修改，无需引入新依赖。
