# ISS-035 — drop cursor 竖线松手后未消失

| 字段 | 内容 |
|------|------|
| ID | ISS-035 |
| 状态 | 已修复 |
| 优先级 | P2 |
| 发现日期 | 2026-05-05 |
| 发现人 | 用户 |
| 环境 | Tauri 客户端（make dev） |

## 现象

拖动块到目标位置松手后，`multiColumnDropCursor` 的蓝色竖线（drop cursor 指示线）仍然残留在页面上，不自动消失。

## 需要排查

1. `MultiColumnDropCursorPlugin` 的 `drop()` 和 `dragend()` handler 是否正确清除 cursor 元素
2. `dragDropEnabled: false`（ISS-034 修复）后，wry 不再触发系统级 drop 事件，导致 ProseMirror 的 `drop` 事件未被派发，cursor 清除逻辑未执行
3. 是否需要在前端监听 `dragend` 事件手动清除

## 视觉增强需求（与 bug 修复合并处理）

用户确认需求：将现有蓝色竖线 drop cursor 替换为淡蓝色半透明区域浮层：

- 拖动块到另一块**左/右边缘**时：高亮目标块的对应半边（左半或右半），淡蓝色半透明
- 拖动块到**上/下位置**时：高亮目标行整行区域，淡蓝色半透明
- 松手后浮层立即消失
- 现有蓝色竖线彻底移除

## 根因分析

### 清除机制分析

源文件：`web/node_modules/@blocknote/xl-multi-column/src/extensions/DropCursor/MultiColumnDropCursorPlugin.ts`

`DropCursorView` 监听四个事件，均注册在 `editorView.dom`（不是 `document`）：

| 事件 | 注册阶段 | 处理逻辑 |
|------|----------|----------|
| `dragover` | bubble | 更新 cursor 位置；调用 `scheduleRemoval(5000)`（5 秒兜底超时） |
| `dragend` | bubble | 调用 `scheduleRemoval(20)`（20ms 后清除） |
| `drop` | **capture** | 直接调用 `setCursor(undefined)` 立即清除 |
| `dragleave` | bubble | 离开编辑器区域时调用 `setCursor(undefined)` |

正常 Web 场景下，松手 → 触发 `drop` → capture 阶段立即执行 `setCursor(undefined)` → cursor 消失。`dragend` 是备用路径（20ms 延迟）。

### ISS-034 引入的根因

`src-tauri/tauri.conf.json` 第 20 行配置了 `"dragDropEnabled": false`。

该配置关闭 wry（macOS 下为 WKWebView）的原生拖放处理。wry 默认会拦截 HTML5 拖放事件并由 Rust 层处理，设为 `false` 后 wry 不再处理拖放，让 WebView 的原生 HTML5 拖放机制生效。

**关键问题**：在 macOS WKWebView 中，`dragDropEnabled: false` 的副作用是：

- `dragend` 事件：由拖起方元素触发，**不依赖 drop 目标**，在拖动结束（无论松手还是取消）时由浏览器派发给拖起元素所在的 `document`。但事件注册在 `editorView.dom`，而块的实际拖动可能由 SideMenu 句柄发起，`editorView.dom` 并非 dragstart 的发起元素，因此 `dragend` 可能在 `editorView.dom` 上冒泡不到。
- `drop` 事件：在 wry 禁用原生拖放后，WKWebView 对 drop 事件的派发行为变为：**只有在 `dragover` handler 调用了 `preventDefault()` 的元素上**才会触发 `drop`。当前 `handleEditorDragOver`（`Editor.tsx`）只对 `blocknote/html` 类型的拖拽调用 `preventDefault()`，且注册在外层 `editor-wrap` div，而 `DropCursorView` 的 drop 监听注册在 `editorView.dom`（内层）。两者层级不同，导致 **`drop` 事件在 `editorView.dom` 的 capture handler 上未被触发**，`setCursor(undefined)` 未执行。

### 结论

**主因**：`dragend` 注册在 `editorView.dom`，WKWebView 环境下该元素不是 dragstart 的发起元素，`dragend` 冒泡路径未经过 `editorView.dom`，导致 20ms scheduleRemoval 未触发。

**次因**：`drop` 事件的 capture handler 依赖于 `editorView.dom` 上的 `preventDefault()` 调用链，而实际的 `preventDefault()` 在外层 wrapper，两层之间事件派发断裂。

**兜底机制失效**：`dragover` 中的 `scheduleRemoval(5000)` 是 5 秒兜底，用户停止拖动后 5 秒内鼠标不移动（不触发 `dragover`）才会清除，体验极差，不是正常清除路径。

## 修复方案

### 方案选择

| 选项 | 描述 | 结论 |
|------|------|------|
| A | 覆盖 cursor element CSS（width/background） | 只解决视觉，不解决残留 bug |
| B | 完全自定义 ProseMirror Plugin 替换 multiColumnDropCursorPlugin | 改动大，需维护 dropPoint/column 逻辑 |
| **C** | **在 Editor.tsx 监听 `dragend` on `document`，直接操作 cursor element** | 最小侵入，复用现有 plugin |

选择方案 C，原因：
- `document` 级别的 `dragend` 在任何拖动结束时都会触发，不依赖 `editorView.dom` 是否在冒泡路径上
- 不需要改动 node_modules 代码
- 视觉改造（竖线→区域浮层）同样可以在 CSS 层面通过 class 覆盖完成，无需替换整个 plugin

### 具体实现

#### 步骤一：修复 dragend 残留（bug fix）

文件：`web/src/components/editor/Editor.tsx`

在 `Editor` 组件的 `useEffect` 中（或新增一个独立 `useEffect`），添加 `document` 级别的 `dragend` 监听，强制清除 cursor element：

```tsx
// ISS-035 修复：WKWebView 环境下 editorView.dom 不是 dragstart 发起元素，
// dragend 无法冒泡到 editorView.dom，需在 document 层兜底清除 drop cursor
useEffect(() => {
  const handleDragEnd = () => {
    // multiColumnDropCursorPlugin 创建的 cursor element 挂在 editorView.dom.offsetParent 下
    // class 为 prosemirror-dropcursor-block 或 prosemirror-dropcursor-inline
    const cursors = document.querySelectorAll<HTMLElement>(
      '.prosemirror-dropcursor-block, .prosemirror-dropcursor-inline'
    );
    cursors.forEach((el) => el.parentNode?.removeChild(el));
  };
  document.addEventListener('dragend', handleDragEnd);
  return () => document.removeEventListener('dragend', handleDragEnd);
}, []);
```

插入位置：紧跟现有 `useEffect(() => { ... }, [onSelectPage])` 之后（约第 697 行之后）。

#### 步骤二：将竖线替换为淡蓝色半透明区域浮层（视觉改造）

利用 `multiColumnDropCursorPlugin` 已给 cursor element 添加的 CSS class 来覆盖样式，无需改动 plugin 本体。

修改 `Editor.tsx` 中 `dropCursor` 配置（约第 533 行），将 `color` 改为透明（不设颜色，通过 CSS class 控制）：

```tsx
// 修改前
dropCursor: (opts) => multiColumnDropCursor({ ...opts, color: "#3b82f6", width: 3 }),

// 修改后（去掉 color/width，改由 CSS class 控制样式）
dropCursor: (opts) => multiColumnDropCursor({ ...opts, color: false, class: "bn-drop-overlay" }),
```

在 `web/src/components/editor/Editor.css` 中新增样式（追加到文件末尾）：

```css
/* ISS-035 — drop cursor 区域浮层替换竖线 */

/* left/right 侧向拖动：半边高亮区域 */
.bn-drop-overlay.prosemirror-dropcursor-vertical {
  /* plugin 计算的 rect 仍是竖线宽度（width=Xpx），需用 CSS 扩展为半块宽 */
  /* 通过 transform + 宽度覆盖实现：以竖线中心为基准，向两侧展开到 50% 父块宽 */
  width: 50% !important;
  /* 将 left 从竖线位置修正为目标块左边缘或右边缘对齐 */
  /* position="left" 时 left 已是块左边 → 不动；position="right" 时 left 是块右边 → 减去 50% */
  /* 由于 CSS 无法直接知道 position 方向，这里用 transform 在两种情况下都偏移正确 */
  /* 实际上 plugin 设置 left = blockRect.left（left方向）或 blockRect.right（right方向）*/
  /* 因此 right 方向需要向左偏移 50% 父宽；这无法纯 CSS 完成，见步骤三 */
  background-color: rgba(59, 130, 246, 0.15) !important;
  border: none !important;
  border-radius: 4px;
}

/* regular 上下拖动：整行高亮区域 */
.bn-drop-overlay.prosemirror-dropcursor-block:not(.prosemirror-dropcursor-vertical) {
  /* plugin 计算的 rect 是水平线（height=Xpx），需扩展为整行高度 */
  height: 28px !important;
  transform: translateY(-50%) !important;
  background-color: rgba(59, 130, 246, 0.12) !important;
  border: none !important;
  border-radius: 4px;
}
```

**注意**：`prosemirror-dropcursor-vertical` class 表示 left/right 侧向位置（见 plugin 第 374-376 行），`prosemirror-dropcursor-block` + 无 `vertical` 表示 regular 上下位置。CSS `!important` 覆盖 plugin 行内 style。

#### 步骤三：left/right 浮层宽度精确定位（可选优化）

由于 plugin 在 `left` 方向将 cursor 的 `left` CSS 设为块左边缘、`right` 方向设为块右边缘，纯 CSS 无法区分两种情况做不同偏移，建议工程师评估以下两种方案：

**方案 3A（推荐）**：接受视觉近似值。`position="left"` 时浮层占据块最左侧 50% 宽（`width: 50%; left: blockRect.left`），符合预期。`position="right"` 时浮层从 `blockRect.right` 开始向右延伸 50%，会超出块右边缘——对多列 UI 可接受，因为右列的下一块就是相邻列。

**方案 3B**：在 `dragover` 时，通过 `MutationObserver` 或在 `handleEditorDragOver` 中检测 `clientX` 相对块的位置，向 cursor element 添加 `bn-drop-left` / `bn-drop-right` CSS class 来区分方向，然后在 CSS 中分别设置 `width` 和 `transform`。

### 验收标准

1. 拖动块到目标位置松手后，蓝色浮层在 ≤100ms 内消失（`document` `dragend` 路径）
2. 拖动取消（Esc 键）后，浮层消失
3. 拖动到块左/右边缘时，显示淡蓝色半透明区域（非竖线）
4. 拖动到块上下位置时，显示全宽淡蓝色横向区域
5. 多列拖入创建新列功能正常（handleDrop 逻辑未改动）
