### 接口契约缺失/不一致

| # | 接口 | 问题 | 建议 |
|---|------|------|------|
| 1 | `POST /api/uploads` 返回 `{ url: string }` | 后端 `uploadResponse` 实际返回 `{ url, name, size, mime }`，但 `Editor.tsx` 中 `FileAttachBlock`、`PdfBlock`、`BookmarkBlock` 的 `fetch` 调用均只断言 `{ url: string }`，丢失了 `name/size/mime` 字段；`FileAttachBlock` 还手工用 `file.name` 和 `file.size` 覆盖，而非使用服务器返回值 | 在 `types/index.ts` 或 `api/client.ts` 定义 `UploadResponse` 接口并导出，Editor.tsx 的上传调用全部使用该类型；同时通过 `api.uploads.upload()` 封装统一获取 |
| 2 | `GET /api/databases/:id/rows` 查询参数 | 后端支持 `sort_col / sort_order / filter_col / filter_op / filter_val`（单列单条件）；前端 `api.databases.listRows` 签名也只传单条 sort/filter。但 `DatabaseView` 的 `sortStates` 和 `filterStates` 都是数组（多列）。服务端能力与前端需求之间存在不匹配 | 后端扩展为接受多条 sort/filter（如 JSON body 或重复参数），或在前端文档中明确「多条件全部本地处理」策略，避免歧义 |
| 3 | `PATCH /api/databases/:id/rows/:row_id`（PatchRow） | 后端只接受 `{ content?: string }`，用于更新行的 BlockNote content；`api.databases.updateRowContent` 调用与此一致。但同一路由如果需要同时更新 `order_index`（如复制行后调整顺序）无法复用，需单独请求 `reorderRows`。接口语义不明确 | 在 handler 注释和前端 `client.ts` 的 JSDoc 中明确 PatchRow 只负责 `content`，顺序更新统一走 `reorderRows`；或将 PatchRow 扩展为通用行字段 patch |
